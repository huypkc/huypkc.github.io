Engineering report

One photo. One sentence. One day.

Verified on deviceIn release validationNot published

The constraint is the product.

One Frame accepts one photograph and one sentence a day. You can rewrite today as often as you like. You cannot fill in yesterday.

That refusal is the whole design. A journal you can backfill becomes a backlog, and a backlog becomes homework. A day you missed stays empty, and the calendar shows the gaps rather than hiding them.

Local-first is the second refusal. Most apps that call themselves private still mean somebody else's server. There is no account here, no upload, and no cloud backup — which also means uninstalling loses everything, so the app says so before you start.

Architecture

Application
Flutter and Dart. Domain, storage and UI kept in separate layers, so no widget and no domain object knows that anything is encrypted.
Journal
SQLite through SQLCipher, opened with a passphrase derived from a 256-bit key.
Photographs
Sealed individually with AES-256-GCM before they reach the disk, each file framed with its own nonce and authentication tag.
Keys
Generated from the platform CSPRNG and held by the Android Keystore — RSA-OAEP-SHA-256 wrapping an AES-GCM store. No key is compiled into the app.
Backup
One encrypted file. Envelope encryption: a random archive key wrapped twice, once by the device key and once by an Argon2id passphrase at 64 MiB and 3 iterations.
Reminders
Local notifications only. Nothing is scheduled off the device.
Language
Vietnamese and English, 120 strings each, chosen by the device. Dates and plurals go through locale-aware formatters, never string concatenation.

What is protected, and what is not.

The journal database, every photograph, and every exported backup are encrypted with keys the operating system holds. That is app-level encryption, and it is a different claim from the sandbox Android puts around every app — a claim worth making only because it was checked.

Privacy Lock is not encryption. It is a screen in the way, for the moment somebody else is holding your unlocked phone. The app says exactly that where you turn it on, because a lock that people mistake for encryption is worse than no lock.

The boundary is stated, not implied. An attacker who has the running, authenticated app, or a rooted device, is not protected against. Nothing here claims otherwise.

Verified by reading the bytes back.

Every line below was run against a Redmi Note 10 Pro holding a real install. A passing test suite cannot tell you what is actually on the disk.

The journal database
The file does not begin with SQLite's signature. Its opening bytes are indistinguishable from noise.
Sentences in that file
Searching the raw bytes for what it stores — the captions, the dates, even the day keys — returns nothing. The whole file yields thirty-two printable fragments, and not one of them is content.
Photographs on disk
Each file opens with the OF1 seal, the system reports it as data rather than an image, and a scan finds zero JPEG markers.
Exported backup
The envelope header carries two independent key wraps and records its own KDF parameters — Argon2id, 64 MiB, 3 iterations.
Backup opened elsewhere
The exported file opened on a separate machine using the passphrase alone, with no access to the phone's Keystore. A wrong passphrase was refused.
Restore onto a new key
The app's data was cleared, which destroys the device key, and the backup restored: ten days and all ten photographs came back.
Task switcher
Screen capture is refused while the app sits in the background, so the journal does not appear in the recents preview.
Biometric unlock
The system log records the prompt completing against this package — the feature was confirmed running, not assumed.

Release engineering

Signed artifact
The release APK carries APK Signature Scheme v2, confirmed by reading the certificate out of the built file.
Artifact inspection
The manifest is read back out of the APK rather than trusted from source: minimum SDK 24, target SDK 36.
Continuous integration
A hosted Android release workflow builds and gates the branch, and has run green against this repository.
Static analysis
The analyzer reports no issues. It is a gate, not a summary — it saw none of the defects below.

Tests

140
Flutter tests passing

They cover the domain rules, the storage boundary, the cipher framing, the backup envelope, migration ordering and the localisation scan.

They also missed five real defects. That is the honest reading of the number, and the reason the section below exists.

Five defects only the hardware could show.

Photographs written around the storage layer

A seeding path wrote image files directly instead of going through the encrypted library, leaving plaintext JPEGs on the phone while every test stayed green.

The lesson: a storage boundary is only a boundary if nothing can reach past it. Found by reading bytes off the device, not by asserting on a mock.

The biometric prompt never appeared

Authentication was wired correctly but hosted by the wrong activity class, and the platform silently declined to show anything.

The lesson: a security feature that cannot be seen running has not been verified. The system log, not the code, settled it.

A settings toggle that would not move

The shell listened to one controller and not to the lock's own, so the switch showed a state the app was no longer in.

The lesson: the smallest visible defect was the one a person would have hit first.

The archive rendered grey tiles

The photo loader was scoped to the home route, so the archive — reached by a push — never received it. In a release build the assertion is stripped, and each failed tile becomes a plain grey box: a dead feature that looks like slow loading.

The lesson: nothing in the suite pushed a route. The regression test now does, and fails without the fix.

A restored journal kept its sentences and lost every photograph

Backups copied each photograph off disk still sealed with the exporting device's key. On the phone that made the backup, nothing looked wrong. Anywhere else — a new phone, or the same phone after a reinstall — every restored photograph was a file nothing could open. That is precisely the case the passphrase exists for.

The lesson: the round-trip test exported and restored with one key, so it could never see this. Photographs now travel unsealed inside the envelope, which already encrypts the payload, and the restoring device seals them with its own key.
